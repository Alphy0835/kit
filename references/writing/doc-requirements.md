# Требование: как записать одной проверяемой фразой

Открывай, когда пишешь раздел требований в ТЗ, нефункциональные требования, ограничения, условия договора
о работе системы. Строение самого ТЗ — `doc-tz.md`. Путь человека по шагам — `doc-use-case.md`.

## 1. Требование и описание — разные тексты

| Текст | Время и слово | Пример |
|---|---|---|
| Требование в ТЗ | «должен», «должна» | «Сервер должен вернуть номер заявки за 2 секунды» |
| Описание работы, юзер-кейс, инструкция | Настоящее время | «Сервер возвращает номер заявки» |

В одном документе слово долженствования одно. «Должен», «следует», «необходимо» вперемешку читаются как три
разные степени обязательности.

## 2. Шесть шаблонов фразы

Метод называется EARS. Его составил Алистер Мавин в Rolls-Royce для требований к авиадвигателю. Порядок частей
всегда один: условия, событие, система, реакция. Условий — сколько угодно, событие — одно или ни одного,
система — ровно одна, реакций — одна или больше.

| Вид | Шаблон | Образец, пример наш |
|---|---|---|
| Постоянное | <Система> должна <реакция> | Форма заявки должна принимать текст задачи длиной до 2000 знаков |
| По событию | Когда <событие>, <система> должна <реакция> | Когда посетитель отправляет заявку, сервер должен сохранить её и вернуть номер за 2 секунды |
| По состоянию | Пока <состояние>, <система> должна <реакция> | Пока заявка в статусе «Новая» дольше 24 часов, панель должна показывать у неё метку «Просрочена» |
| Нежелательное | Если <сбой>, то <система> должна <реакция> | Если сервер не сохранил заявку, то форма должна показать сообщение об ошибке и сохранить введённый текст |
| Необязательная возможность | Если включено <что>, <система> должна <реакция> | Если включён приём заявок через Telegram, бот должен принимать от одного человека не больше одной заявки за 10 минут |
| Сложное | Пока <состояние>, когда <событие>, <система> должна <реакция> | Пока идёт обслуживание, когда посетитель открывает страницу заявки, сайт должен показать время возобновления работы |

Русские шаблоны — наш перевод. В оригинале ключевые слова: While, When, Where, If — then.

Где метод не годится: требование с десятком условий, сложная логика, ограничения архитектуры. Там нужна
таблица решений или схема состояний.

## 3. Признаки хорошего требования

Девять признаков по стандарту ISO/IEC/IEEE 29148:2018:

| Признак | Вопрос |
|---|---|
| Необходимое | Что сломается, если его убрать |
| Без лишних ограничений | Не названа ли технология или экран там, где важен результат |
| Однозначное | Можно ли понять его вторым способом |
| Полное | Понятно ли оно без соседних |
| Единичное | Одна ли в нём реакция |
| Осуществимое | Можно ли это сделать в срок и бюджет |
| Проверяемое | Как доказать, что оно выполнено |
| Верное | То ли оно говорит, что нужно заказчику |
| По шаблону | Записано ли оно так же, как остальные |

К набору требований те же вопросы задаются в целом: нет ли дыр и нет ли двух требований, которые спорят.

## 4. Слова, которых нет в требовании

Слово допустимо, только когда рядом стоит мера, граница или определение.

| Вид | Слова | Что вместо |
|---|---|---|
| Оценка | удобный, простой, понятный, гибкий, надёжный, современный, эффективный | Число и способ измерения |
| Расплывчатое количество | несколько, много, около, примерно, порядка | Число и единица |
| Расплывчатая мера | быстро, оперативно, своевременно, достаточно, приемлемо | Срок и условие нагрузки |
| Превосходная степень | лучший, оптимальный, максимальный, минимальный | Порог |
| Сравнение без базы | быстрее, лучше, качественнее | С чем сравнивается и на сколько |
| Лазейка | по возможности, при необходимости, если применимо, как правило | Условие «если <событие>» |
| Открытый перечень | и так далее, и другие, в том числе, как минимум | Полный перечень |
| «и/или», косая черта | и/или, да/нет | Два требования |
| Всеобщность | все, любой, оба | «Каждый» или перечень |
| Местоимение | он, она, это, который | Название предмета |
| Пустое обязательство | поддерживать, обрабатывать, обеспечивать, позволять | Что именно делает и с каким итогом |
| Неточное время | в итоге, со временем, после этого, как только | Событие и срок |
| Ссылка в никуда | см. выше, как раньше | Номер требования |
| Недосказанность | уточнить позже, будет определено | Требование не пишется, вопрос идёт заказчику |
| Решение вместо нужды | «на Redis», «кнопка слева сверху» | Результат. Решение — только с обоснованием |

Было: «Система должна быстро обрабатывать заявки».
Стало: «Сервер должен сохранить заявку и вернуть номер за 2 секунды при 20 заявках в минуту».

Было: «Панель должна быть удобной».
Стало: «Новый менеджер должен найти заявку по номеру телефона за 1 минуту без подсказок».

## 5. Правила фразы

Из руководства INCOSE по написанию требований, версия 4, 42 правила. Здесь те, что подтверждены:

- Подлежащее — тот, кто отвечает: система или её часть. Залог действительный.
- Одно требование — одно предложение. Союз «и» между двумя реакциями — знак, что требований два.
- Каждый термин есть в словаре документа.
- Единицы измерения одни на весь документ.
- Отрицание — только там, где иначе не сказать: «должен хранить 30 дней», а не «не должен удалять раньше».
- Сокращение расшифровано, многозначных сокращений нет.
- Показатель измерим: число, единица, условие.

## 6. Карточка требования

Шаблон Volere даёт 13 полей. Для малого проекта хватает пяти:

| Поле | Что в нём |
|---|---|
| Номер | Постоянный, не переиспользуется |
| Описание | Фраза по шаблону из раздела 2 |
| Обоснование | Зачем: одна фраза |
| Критерий соответствия | Измерение, по которому видно, что требование выполнено |
| Источник | Кто попросил |

Правило Volere: у каждого требования есть критерий соответствия. Не получается его написать — требование
неясно или плохо понято.
