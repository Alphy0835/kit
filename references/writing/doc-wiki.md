# Вики проекта и комплект передачи

Открывай, когда заводишь либо чистишь вики проекта (Confluence, Notion, папка `docs/`), пишешь страницу для неё
либо готовишь проект к передаче другой команде. Отдельные виды страниц — в своих файлах: инструкция и рунбук —
`doc-howto.md`, запись решения и архитектура — `doc-architecture.md`, README — `doc-readme.md`.

## 1. Шесть правил вики

1. **Мало, но верно.** Десять точных страниц полезнее ста устаревших. Страница, которой не верят, вредит
   соседним: читатель перестаёт верить всем.
2. **У страницы есть владелец и дата проверки.** Общая вики Google без владельцев и порядка добавления
   заросла дублями и ошибками. Помогли владельцы, ревью правок и хранение в системе версий.
3. **Один факт — одно место.** Во втором месте стоит ссылка. Копия устаревает первой.
4. **Что меняется вместе с кодом — правится в той же правке, что и код.**
5. **Любая страница может оказаться первой.** Читатель приходит из поиска, а не с главной. Страница сама
   говорит, о чём она и для кого, и даёт ссылку вверх.
6. **Раздел появляется вместе с первой страницей.** Пустых разделов «на вырост» нет.

## 2. Что лежит в вики и что в репозитории

Источники единого ответа не дают. На деле ведут оба места и ставят ссылки.

| Что | Где | Почему |
|---|---|---|
| Запуск, сборка, тесты, выкладка, откат | Репозиторий, `docs/` | Меняется вместе с кодом, проверяется в той же правке |
| Устройство системы, схема данных, записи решений | Репозиторий, `docs/` | То же; агент читает это вместе с кодом |
| Описание API | Собирается из кода: `doc-api.md` | Расходится, если писать отдельно |
| Правила и договорённости, которые правит заказчик | Вики | Заказчик не работает с Git |
| Доступы и их владельцы, контакты, порядок эскалации | Вики с ограничением прав | Меняется без правки кода |
| Протоколы встреч, планы, статусы | Вики | Привязаны ко времени, с кодом не связаны |
| Разборы сбоев | Одно место на выбор команды | Важно, чтобы все лежали вместе |

Правило для границы: у факта одно место-эталон. Со второй стороны стоит ссылка и слова «эталон — там».

## 3. Разделы верхнего уровня

Набор для малой команды. Сведён из руководств Google, Microsoft и практик Confluence; целиком ни в одном
источнике не стоит.

| Раздел | Что внутри |
|---|---|
| Начало | Для чего проект, кто владелец, куда идти дальше. Только ссылки, один экран |
| Как устроено | Обзор системы: части, данные, связи с чужими системами, границы |
| Как запустить и выложить | Запуск с нуля, сборка, тесты, выкладка по средам, откат |
| Как у нас принято | Ветки, ревью, что значит «готово», правила названий |
| Решения | Записи решений и сравнения вариантов |
| Эксплуатация | Рунбуки, доступы и их владельцы, резервные копии |
| Сбои | Разборы после сбоев |
| Словарь | Слова проекта |
| Архив | Закрытое и устаревшее |

- Вложенность — до трёх уровней. Число взято из практик Confluence по выдаче поиска, нормой не является.
- Страница-указатель состоит из ссылок. Содержания на ней нет.
- Дерево строится по задачам читателя, а не по устройству команды.

## 4. Шапка и строение страницы

**Шапка:**

```
Владелец: <имя либо роль>
Проверено: ГГГГ-ММ-ДД
Статус: черновик | действует | устарел
Для кого: <кто читает и что он уже знает>
```

- **Владелец** отвечает на вопросы по странице и решает, жива ли она. Уходит владелец — страница передаётся.
- **Проверено** — день, когда владелец перечитал страницу и сверил её с делом. Дата правки её не заменяет:
  исправленная опечатка не делает страницу проверенной.
- **Устарел** — страница оставлена ради истории. В первой строке стоит ссылка на замену.

**Название:**

- Слова, по которым страницу будут искать: «Как выложить сервер заявок», а не «Деплой, заметки».
- Пустых слов «Обзор», «Введение», «Разное» в названии нет.
- Дата в названии — только у страниц, привязанных ко времени: встреча, план. Формат один: ГГГГ-ММ-ДД.
- Двух страниц с одним названием нет.

**Начало страницы:**

- Первые фразы отвечают: о чём страница, для кого, когда её открывать. Читатель за секунды понимает, туда ли
  он попал.
- Страница не для этого читателя — в начале сказано, куда ему идти.
- Вывод стоит в начале, подробности — ниже.

**Тело и связи:**

- Одна страница — один вид текста: понятие, задача, справка либо поиск неисправности. Виды — `doc-types.md`.
- Заголовки идут по уровням без пропусков. Нужен четвёртый уровень — пора делить страницу.
- Текст ссылки называет страницу, на которую она ведёт. Слова «здесь» и «тут» ссылкой не служат.
- В конце — «См. также»: ссылка вверх, на раздел, и на соседние страницы.

## 5. Виды страниц, которых нет в других файлах

### Введение для новичка

Указатель со ссылками. Содержание лежит на страницах, на которые он ведёт. Шесть частей по шаблону Microsoft:

1. Цель проекта: что он даёт и как понять, что он успешен.
2. Люди: кто за что отвечает и как с ним связаться.
3. Как команда работает: ссылка на «Как у нас принято».
4. Настройка рабочего места: шаги от пустой машины до работающего проекта, с версиями программ.
5. Устройство проекта: репозитории, среды, выкладка.
6. Где что лежит: беклог, вики, история.

Проверка страницы — проба: новичок по ней ставит проект и вносит первую правку. Место, где он застрял, —
дефект страницы, его чинят сразу. Мера — время до первой правки, проверенной на своей машине.

### Обзор системы

Готового шаблона источники не дают. Состав — предложение тим лида:

1. Что система делает и для кого — два-три предложения.
2. Границы: что в неё входит и что нет.
3. Части и связи между ними — схема. Правила схем — `doc-architecture.md`.
4. Путь данных: откуда приходят, где лежат, куда уходят.
5. Чужие системы: с чем связана и что будет, когда они недоступны.
6. Куда смотреть при сбое: журналы, панели, рунбуки.

Обзор может быть неполным. Он нужен, чтобы понять систему, а не чтобы перечислить всё.

### Запись на тревогу

Рунбук вообще — `doc-howto.md`, раздел 8. Здесь — запись, привязанная к одной тревоге мониторинга.

- Запись заводится вместе с тревогой. Тревоги без записи нет.
- Состав: что значит тревога; насколько это серьёзно и кого задевает; как убедиться, что она настоящая; как
  снять остроту; как устранить причину; кого звать, если не вышло.
- Секретов в записи нет. Стоит место, где секрет лежит.
- Запись превратилась в постоянный список команд — это повод написать скрипт.
- Дежурный, которому запись не помогла, правит её сразу после сбоя.

### Статья базы знаний

Короткая запись «проблема — решение» для повторяющихся обращений. Состав по KCS:

1. Заголовок — словами того, кто обратился: по ним статью будут искать.
2. Проблема: что человек видит.
3. Среда: версия, роль, условия, при которых это случается.
4. Решение: шаги.
5. Причина.

Правила: сначала ищи статью, потом решай — так нет дублей. Статья пишется в ходе работы, а не потом.
Воспользовался статьёй — проверил её: нашёл ошибку — исправь либо пометь.

### Разбор после сбоя

- Пишется по условиям, названным заранее: простой дольше порога, потеря данных, ручной откат, долгое устранение.
- Состав: что случилось и когда, по времени; кого и как задело; что сделали, чтобы снять остроту; причины; что
  делаем дальше — задачи с исполнителем и сроком.
- Виноватых разбор не ищет. Он описывает, как устройство системы и порядок работы дали ошибке случиться.
- Личных данных клиентов в разборе нет.
- Разбор, который никто не прочитал, не считается сделанным.
- Все разборы лежат в одном месте.

### Словарь

- Только слова проекта и заказчика. Общеизвестные слова в словарь не идут.
- Запись: слово, сокращение, определение в одном–трёх предложениях, источник.
- Рядом — слова, которыми это называть не надо: «не „лид“, а „заявка“».
- Слово в текстах проекта пишется так, как в словаре: `text-ste100.md`, правило «одно слово — один смысл».

### Как у нас принято

Договорённости команды: ветки и слияния, порядок ревью, что значит «готово», правила названий, чек-листы.
Страница короткая. Каждое правило — одна строка и причина. Правило, которое никто не соблюдает, удаляется либо
начинает проверяться машиной.

## 6. Комплект передачи проекта

Стандарта нет. Список сведён из чек-листов практиков: Хабр 2022, vc.ru 2025, Miquido, Mad Devs, руководство
Microsoft.

**Мерило.** Передача удалась, когда новая команда сама ставит проект, запускает, выкладывает и вносит правку,
не спрашивая прежних авторов. Проверяется пробой, а не чтением.

| № | Что передать | Что внутри |
|---|---|---|
| 1 | Назначение | Для кого проект, что он даёт, история, ближайшие цели, беклог с приоритетами |
| 2 | Обзор системы | Части, схема данных, связи с чужими системами, ограничения |
| 3 | Код | Репозитории, назначение веток, сборка и выкладка, незакрытые задачи |
| 4 | Запуск с нуля | Среды, переменные окружения, сторонние сервисы, шаги выкладки. Проверено пробой на чистой машине |
| 5 | Инфраструктура | Серверы, домены, базы и копии, фоновые задачи, сертификаты и их сроки |
| 6 | Доступы | Один список: что, где, кто владелец. Сами секреты передаются отдельным защищённым путём |
| 7 | Решения и причины | Почему сделано так. Временные обходы, отложенное, слабые места |
| 8 | Качество | Какие тесты есть и как их запустить, известные дефекты |
| 9 | Эксплуатация | Мониторинг, тревоги, рунбуки, известные отказы, кого звать |
| 10 | Люди и порядок | Контакты, договорённости, подрядчики и оплаты |
| 11 | Карта документации | Где что лежит и что из этого устарело |

Правила передачи:

- Чаще всего теряется строка 7 — «почему». В коде этого не видно, а спросить будет некого.
- Учётные записи и репозитории принадлежат заказчику либо новой команде, а не уходящему человеку. Это
  проверяется до передачи.
- Всё, чем пользуются в работе, лежит в репозитории, включая скрипты с личных машин.
- Документы надёжнее, когда их пишет принимающий: уходящий объясняет, принимающий записывает, уходящий
  проверяет. Так пробелы видны сразу.
- Прежняя команда остаётся на связи на переходный срок. В разгар выпуска проект не передают.

## 7. Как держать вики свежей

Правила для людей:

1. Страница правится в той же задаче, что и предмет, который она описывает.
2. Владелец перечитывает страницу к сроку и ставит новую дату проверки. Срок выбирает команда: раздел 9.
3. Воспользовался страницей и нашёл ошибку — исправь либо напиши владельцу.
4. После сбоя задаётся вопрос: «помогла ли страница?»
5. Устаревшее убирается из живых разделов. Удалять либо складывать в архив — решает команда: раздел 9.
6. Один человек следит за порядком в разделе: названия, дубли, архив.
7. Правку читает второй человек. Три взгляда: верно ли по делу, понятно ли читателю, ровно ли по тексту.

Что проверяет машина:

| Что | Как |
|---|---|
| Битые внутренние ссылки | Проверка ссылок в сборке: `mlc`, Sphinx `linkcheck`. Внешние ссылки дают предупреждение, сборку не останавливают |
| Страница без владельца | Проверка поля в шапке |
| Просроченная проверка | Поиск по дате в шапке. В Notion — срок подтверждения страницы и уведомление владельцу |
| Код изменился, страница нет | Сравнение дат правки кода и страницы; правило «правка без описания не принимается» |
| Ссылки на файлы, которых нет, в файлах для модели | В Claude Code — `/doctor prompt-audit` |
| Орфография и слова из запретного списка | Линтер текста в сборке |

Машина не видит, верна ли страница, нужна ли она ещё и понятна ли новичку. Это видят ревью и проба новичком.
Имена инструментов взяты из пересказов; перед записью в скрипт каждое проверяется запуском.

## 8. Страницы, которые читает модель

Файл для модели (`CLAUDE.md`, `AGENTS.md`) — короткий указатель, а не пересказ вики.

- **Размер.** До 200 строк. Так советует документация Claude Code: длинный файл соблюдается хуже.
- **Что писать.** Команды, которые модель не угадает. Правила, которые расходятся с общепринятыми. Как запустить
  тесты. Решения по устройству проекта. Неочевидные ловушки.
- **Чего не писать.** То, что видно из кода. Общие правила языка. Описание файлов по одному. Обзор репозитория.
  Подробную справку — на неё ставится ссылка. Слова вроде «пиши чистый код».
- **Проверка строки.** «Уберу строку — модель начнёт ошибаться?» Нет — строка лишняя.
- **Противоречий нет.** Из двух правил, которые спорят, модель выбирает любое.
- **Файл правится как код:** когда модель ошиблась, и с чисткой.

Исследование Gloaguen и др. (ICLR 2026) измерило файлы для агентов: доля решённых задач в среднем не выросла,
стоимость выросла больше чем на 20 %, обзоры репозитория не помогли. Польза была у правил, которых модель не
может вывести сама. Отсюда правило «коротко и только неочевидное».

Страницы вики для модели пишутся так же, как для человека из правила 5 раздела 1: страница понятна без
соседних. Модель, как и человек из поиска, открывает одну страницу.

## 9. Что решает команда

Источники расходятся. Колонка «Берём» — предложение тим лида от 14.10.2026, владелец её не утверждал.

| Вопрос | Стороны | Берём |
|---|---|---|
| Вики либо репозиторий | Google и Spotify — рядом с кодом. Notion и Confluence — владельцы и сроки без Git | Оба места по таблице раздела 2 |
| Удалять либо в архив | Google — в сомнении удалять. Практики Confluence и KCS — архив | В репозитории удалять: история остаётся в Git. В вики — архив вне поиска |
| Срок проверки | Книга Google — около трёх месяцев как пример. Практики Confluence — 90 дней. Нормы нет | Эксплуатация и доступы — 3 месяца, остальное — 6. Числа наши |
| Кто пишет документы при передаче | Хабр и vc.ru — уходящий. Understand Legacy Code — принимающий | Принимающий записывает, уходящий проверяет |
| Одна запись на вид тревоги либо шаги на каждую | SRE Workbook называет вопрос спорным и советует выбрать одно | Шаги на каждую тревогу: читатель может быть новичком |
