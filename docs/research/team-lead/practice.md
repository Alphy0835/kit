## 1. Ревью кода у людей

### 1.1. Ревью находит меньше дефектов, чем от него ждут
- Источник: Bacchelli, Bird. «Expectations, Outcomes, and Challenges of Modern Code Review». ICSE 2013. https://sback.it/publications/icse2013.pdf (открывал).
- Что показано: Microsoft, 17 интервью, анкеты 165 менеджеров и 873 разработчиков, разбор 570 комментариев из 200 веток ревью. Поиск дефектов — главная причина ревью для 44% разработчиков и 44% менеджеров. Но в комментариях дефекты — только четвёртая категория из девяти: 78 из 570 (14%). Из них 65 — логические мелочи (например, неверное условие), 6 — высокий уровень, 5 — безопасность, 3 — исключения. Самая частая категория — улучшение кода, 165 (29%): практики, лишний код, читаемость.
- Для тим лида: ревью diff глазами — в основном правки вида и читаемости плюс мелкая логика. Глубокие дефекты (дизайн, безопасность) оно ловит редко. Их надо ловить тестами и проверкой по критериям.

### 1.2. Главная трудность ревью — понять, зачем правка
- Источник: тот же Bacchelli, Bird 2013 (открывал).
- Что показано: понимание изменения названо главной трудностью. Цитата из интервью: самое трудное — понять причину изменения. Те, кто начинал с текстового описания, тратили на первый комментарий заметно больше времени. Часть комментариев — просьбы объяснить, зачем правка.
- Для тим лида: задание и отчёт исполнителя должны отвечать на «зачем» и «что считать готовым». Если исполнитель не написал причину, ревью превращается в угадывание.

### 1.3. Google: мелкие правки, один ревьюер, быстро
- Источник: Sadowski, Söderberg, Church, Sipko, Bacchelli. «Modern Code Review: A Case Study at Google». ICSE-SEIP 2018. https://storage.googleapis.com/gweb-research2023-media/pubtools/4476.pdf (открывал, текст из PDF).
- Что показано: 12 интервью, анкета 44 человек, журналы около 9 млн правок. Медиана размера правки — 24 строки. Больше 10% правок — одна строка. Около 90% правок трогают меньше 10 файлов. Больше 80% правок идут не больше чем с одним ревьюером, меньше 25% — с несколькими. Медиана времени всего ревью — меньше 4 часов, первый отклик по малым правкам — меньше часа. Число комментариев растёт с размером правки: пик 12,5 комментария у правок около 1250 строк. Только 2 респондента из анкеты сказали, что комментарии нашли баг. Ревью воспринимают как групповое решение задач, обучение и поддержку читаемости. Названные трудности: расстояние между автором и ревьюером, социальные трения, неясность, когда ревьюить дизайн, нехватка контекста («что вызвало правку»).
- Для тим лида: резать задачи так, чтобы diff был маленьким. Контекст «что вызвало правку» давать заранее. Ревью — не главный ловец багов, ждать от него этого не надо.

### 1.4. Слабое ревью связано с дефектами после выпуска
- Источник: McIntosh, Kamei, Adams, Hassan. «The Impact of Code Review Coverage and Code Review Participation on Software Quality». MSR 2014. https://rebels.cs.uwaterloo.ca/papers/msr2014_mcintosh.pdf (открывал, текст из PDF).
- Что показано: проекты Qt, VTK, ITK. Покрытие ревью — доля правок, прошедших ревью. Участие — глубина ревью: доля правок без обсуждения, доля правок, одобренных самим автором, доля ревью быстрее 200 строк в час («поспешные»). Низкое покрытие и низкое участие дают до 2 и до 5 лишних дефектов после выпуска на компонент. Для Qt 5.0.0: доля проревьюенных правок ниже 0,6 — не меньше одного дефекта, ниже 0,06 — не меньше двух. Доля правок без обсуждения выше 0,71 — не меньше двух дефектов, выше 0,9 — не меньше трёх. Эффект не везде значим: покрытие значимо в двух из четырёх моделей.
- Оговорка: это связь, не причина. Компонент без ревью мог быть просто сырым.
- Для тим лида: «одобрил, не вглядываясь» — реальный риск. Принять без вопросов и без запуска проверок хуже, чем потратить минуту на вопрос исполнителю.

### 1.5. Размер правки и скорость просмотра (Cisco / SmartBear)
- Источник: SmartBear. «Best Practices for Code Review». https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/ (открывал).
- Что показано: по исследованию команды Cisco не стоит ревьюить больше 200–400 строк за раз; за 400 строк способность находить дефекты падает. Ревью 200–400 строк за 60–90 минут должно давать 70–90% найденных дефектов. Темп — медленнее 500 строк в час. Сеанс — не дольше 60 минут. Автор заранее комментирует свой код, это снижает плотность дефектов. Выборочная проверка 20–33% кода снижает плотность дефектов при малых затратах. Лёгкое ревью занимает меньше 20% времени формального и находит столько же багов. Размер выборки и метод на странице не указаны.
- Оговорка: это материал вендора, не рецензируемая работа. Первичный отчёт Cisco я не нашёл. Цифры ориентировочные.
- Для тим лида: около 400 строк в одном diff — разумный потолок. Выше «смотреть целиком» бессмысленно: ветку надо резать или принимать по частям. Просить исполнителя пояснить свой diff в отчёте — совпадает с 1.2.

### 1.6. Формальные инспекции Fagan
- Источник: упоминание у McIntosh 2014 (открывал): Fagan показал, что формальные инспекции со встречами снижают число ошибок на этапе тестирования. В современном ревью встреч и обязательных чек-листов нет. Сам Fagan 1976 — не открывал.
- Для тим лида: формальная процедура не нужна. Но строгость стоит задавать заранее (пункты приёмки в задании), а не «на глаз».

## 2. Разбор причин и что после него

### 2.1. Google SRE: разбор без вины, ревью разбора, действия
- Источник: Google SRE Book, глава «Postmortem Culture: Learning from Failure». https://sre.google/sre-book/postmortem-culture/ (открывал).
- Что показано: разбор фиксирует инцидент, влияние, шаги смягчения, корневые причины и дальнейшие действия. Поводы для разбора заданы заранее (потеря данных, простой выше порога, ручное вмешательство). Черновик проходит ревью старших инженеров: достаточно ли глубока причина, верны ли приоритеты действий. Цитата в смысле: неревьюенный разбор всё равно что не существовал. Принцип «без вины»: людей не починить, систему и процессы можно. Данных об эффективности в главе нет: ни частоты повторов, ни доли выполненных действий. Подтверждение — рассказы.
- Для тим лида: «причина возврата задачи» — это разбор. Поводы стоит задать заранее (возврат, баг, найденный после приёмки). Данных, что разбор снижает повторы, в первоисточнике нет.

### 2.2. Atlassian: срок на действия и напоминания
- Источник: Atlassian. «Incident management handbook». https://pages.eml.atlassian.com/rs/594-ATC-127/images/Atlassian-incident-management-handbook-.pdf (открывал, текст из PDF).
- Что показано: цель процесса — предотвращать повторы через обучение на инцидентах и «почти-инцидентах». Разбор без вины; ревью и утверждение разбора руководством задают нужную строгость. Значимые меры получают договорённый срок выполнения (SLO), в большинстве случаев 8 недель, с напоминаниями и отчётами. Формулировка действия (по Lueder и Beyer): с глаголом и полезным результатом, узкая по охвату, с видимым признаком завершения. Пример из справочника: «добавить оповещение, когда сервис отдаёт больше 1% ошибок» годится, «исследовать мониторинг» не годится. Количественных данных об эффекте нет.
- Для тим лида: действие после разбора — тоже задача: с глаголом, узкая, с признаком завершения, владельцем и сроком. Иначе оно не будет сделано.

### 2.3. Etsy
- Источник: John Allspaw, «Blameless PostMortems and a Just Culture» (2012). Atlassian ссылается на него. Страницу открыть не удалось (ответ 403) — не открывал.

## 3. Агенты: документация и статьи

### 3.1. Anthropic: оркестратор и исполнители, оценщик
- Источник: Anthropic. «Building effective agents». https://www.anthropic.com/engineering/building-effective-agents (открывал).
- Что показано: оркестратор сам режет задачу на подзадачи по входу и отдаёт исполнителям (подходит для правок по многим файлам). Схема «оценщик–улучшатель» годится, когда есть ясные критерии оценки и итерации дают измеримую пользу. Усложнять стоит, только когда это доказуемо улучшает результат. Агент должен на каждом шаге получать «землю» из среды (результат вызова, запуск кода). Код проверять проще: тесты дают обратную связь. Человек нужен, чтобы подтвердить соответствие требованиям системы. Нужны границы, например максимум итераций.
- Для тим лида: у задачи должны быть проверки, которые агент может запустить сам. Оценщик работает только по заранее заданным критериям. Нет критериев — оценивать нечем.

### 3.2. Anthropic: как лид ставит задачу субагентам
- Источник: Anthropic. «How we built our multi-agent research system». https://www.anthropic.com/engineering/multi-agent-research-system (открывал).
- Что показано: каждому субагенту нужны цель, формат результата, указания по инструментам и источникам и чёткие границы. Пример расплывчатой команды: «исследуй дефицит полупроводников» — один субагент взял кризис 2021, два других дублировали работу по 2025. Ранние версии плодили 50 субагентов на простые вопросы. Правила масштаба усилий вписаны в подсказку лида. Лид на Opus 4 с субагентами на Sonnet 4 обошёл одиночный Opus 4 на 90,2% на внутренней проверке исследований. На BrowseComp расход токенов объясняет около 80% разброса качества. Мультиагентная система тратит примерно в 15 раз больше токенов, чем чат. Оценка: судья-модель одним запросом (оценка 0,0–1,0 и зачёт/незачёт) совпала с людьми лучше всего, но люди-тестеры замечали то, что автоматика пропускала. Сами авторы пишут: многоагентные системы плохо подходят задачам с общим контекстом и многими зависимостями, «например, большей части программирования».
- Для тим лида: задание исполнителю = цель + формат результата + границы (что не трогать) + чем проверять. Без этого исполнители дублируют друг друга и уходят не туда. Для кода делить на независимые куски.

### 3.3. Claude Code: проверка, независимое ревью, субагенты
- Источник: документация Claude Code, «Best practices». https://code.claude.com/docs/en/best-practices (открывал).
- Что показано:
  - Claude останавливается, когда работа «выглядит готовой». Без проверки, которую он может запустить, это единственный сигнал. Нужно дать тесты, сборку, линтер или сравнение скриншотов.
  - Просить доказательства, а не утверждение: вывод тестов, команду и её результат, скриншот. Смотреть доказательство быстрее, чем перезапускать проверку самому.
  - «Второе мнение»: проверяющий субагент со свежим контекстом видит только diff и критерии, не рассуждения автора.
  - Предупреждение: ревьюер, которого попросили искать пробелы, почти всегда их найдёт, даже если работа в порядке. Погоня за каждой находкой ведёт к лишним слоям и тестам на невозможное. Ревьюеру надо сказать: сообщай только о том, что влияет на корректность или заявленные требования.
  - Самодостаточная спецификация: названы файлы и интерфейсы, указано, что вне задачи, в конце есть сквозная проверка.
  - Две неудачные поправки подряд: очистить контекст и написать задачу точнее.
  - Ошибка «доверяй, потом проверяй»: правдоподобная реализация без краевых случаев; лекарство — всегда давать проверку.
- Источник: Claude Code, «Subagents». https://code.claude.com/docs/en/sub-agents (открывал, первые 100 тыс. знаков из 111 тыс.).
- Что показано: субагент стартует с чистым контекстом и не видит переписку; он получает свой системный промпт, сообщение с задачей и CLAUDE.md. Результат — его итоговый отчёт. Много подробных отчётов всё равно съедают контекст лида. Вложенность разрешена до трёх уровней.
- Для тим лида: ревьюеру передавать diff, критерии и правило «сообщай только о влиянии на корректность и требования». Требовать от исполнителя доказательства в отчёте. Субагенту всё нужное писать в сообщении: он не знает того, что знает лид.

### 3.4. OpenAI: инструкции агентам
- Источник: OpenAI. «A practical guide to building agents». https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf (открывал, текст из PDF).
- Что показано: чёткие инструкции снижают двусмысленность и ошибки. Практики: опираться на существующие документы, просить разбить задачу на малые шаги, каждому шагу задать конкретное действие или результат, описать краевые случаи. Сначала выжать максимум из одного агента; несколько агентов добавляют сложность. Начинать с проверок (evals) для базовой линии.
- Для тим лида: тот же вывод, что у Anthropic. В задании нужны шаги и краевые случаи, а не «сделай хорошо».
- Google: первоисточника по постановке задач агентам я не нашёл.

## 4. Модель как судья и ревьюер

### 4.1. Искажения судьи-модели
- Источник: Zheng и др. «Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena». NeurIPS 2023. https://arxiv.org/html/2306.05685v4 (открывал).
- Что показано: согласие GPT-4 с людьми — 85% (без ничьих), между людьми — 81%. Но есть искажения. Позиция: при смене порядка ответов судья остаётся при своём мнении у GPT-4 в 65,0% случаев, у GPT-3.5 в 46,2%, у Claude-v1 в 23,8%. Длина: на атаку «повторяющийся список» Claude-v1 и GPT-3.5 ошиблись в 91,3% случаев, GPT-4 в 8,7%. Своё: GPT-4 выигрывал на своих ответах примерно на 10% чаще, чем людей, Claude-v1 на 25%, но авторы пишут, что данных мало и вывод об этом искажении сделать нельзя. Математика и рассуждения: ошибка судьи 14 из 20 по умолчанию, 6 из 20 при цепочке рассуждений, 3 из 20, когда судье дан эталонный ответ.
- Для тим лида: судья, в том числе ревьюер-субагент, не эталон. Давать ему эталон или тесты, смотреть в двух порядках. Длинный отчёт исполнителя не значит хороший.

### 4.2. Модель узнаёт и предпочитает свои ответы
- Источник: Panickssery и др. «LLM Evaluators Recognize and Favor Their Own Generations». 2024. https://arxiv.org/abs/2404.13076 (открывал только аннотацию).
- Что показано: GPT-4 и Llama 2 отличают свои тексты от чужих и человеческих «с нетривиальной точностью». Есть линейная связь между умением узнавать себя и силой предпочтения своего. Эксперименты говорят, что причинная связь «устоит перед простыми помехами», но не доказывают её.
- Для тим лида: ревьюер той же модели, что исполнитель, может быть мягче к чужой ветке. Сильнее помогают тесты и критерии, чем смена контекста.

### 4.3. Точность модели как проверяющего код
- Источник: Cihan, İçöz, Haratian, Tüzün. «Evaluating Large Language Models for Code Review». 2025. https://arxiv.org/pdf/2505.20206 (открывал, текст из PDF).
- Что показано: GPT-4o и Gemini 2.0 Flash, 492 блока кода с известной корректностью (по юнит-тестам) и 164 эталонных блока HumanEval. С описанием задачи верно оценивают корректность 68,50% и 63,89%, правят код верно в 67,83% и 54,26%. Без описания хуже. До 24,80% правильных блоков получили неправильную правку («регрессия»). Худший случай (Gemini без описания): неверные решения «одобрить» в 44,44%. На эталонных блоках результат другой: Gemini 66,67% против GPT-4o 42,07%. Вывод авторов: полностью автоматическое ревью ненадёжно, нужен человек в цикле, описание задачи заметно помогает.
- Для тим лида: ревьюеру без описания задачи верить ещё меньше. Всегда давать ему задание и критерии. Одобрение моделью не заменяет тесты.

### 4.4. Доля отклонённых замечаний ИИ-ревьюера
- Источник: Lin, Liang, Thongtanunam, Tantithamthavorn. «Is Agentic Code Review Helpful? Mining Developers' Feedback to CodeRabbit Reviews in the Wild». arXiv 2607.03316, июль 2026. https://arxiv.org/abs/2607.03316 (открывал только аннотацию).
- Что показано: 31 073 пары «комментарий ревью — реакция разработчика», 10 191 pull request, 239 репозиториев, один инструмент (CodeRabbit). Принято 36,4%, вызвало обсуждение 7,3%, отклонено 56,3%. Причины отклонения: неверные замечания (ложные, повторные, вне объёма) и несовпадение с практикой и намерением разработчика. Доли причин в аннотации не даны. Замечания по функциональности чаще неверны, чем по читаемости.
- Оговорка: один инструмент; реакция разработчика не равна правоте замечания.
- Для тим лида: больше половины замечаний ИИ-ревьюера в реальных репозиториях не приняли. Каждое замечание субагента перепроверять по diff и тестам, прежде чем возвращать ветку на доработку.

### 4.5. Агент пишет «готово» о несделанном и как это ловят
- Источник: Anthropic. «Effective harnesses for long-running agents». https://anthropic.com/engineering/effective-harnesses-for-long-running-agents (открывал).
- Что показано: типовые сбои — «объявить победу рано» (агент видит сделанное и решает, что всё готово) и «отметить функцию сделанной без проверки» (опирался на юнит-тесты и curl, сквозь систему не проверял). Лекарство: список функций в JSON, все изначально «не проходят»; агент меняет только поле passes; удалять или править тесты «недопустимо»; одна функция за сессию; сквозная проверка через браузер «как человек»; в начале сессии базовый сквозной тест, чтобы увидеть сломанное состояние. Чисел нет.
- Для тим лида: критерии приёмки устроить как этот список: проходит или нет, исполнитель критерии не переписывает, в diff смотреть правки тестов. Сквозная проверка, а не «юнит-тесты зелёные».
- Источник: METR. «Recent Frontier Models Are Reward Hacking». 2025. https://metr.org/blog/2025-06-05-recent-reward-hacking (открывал).
- Что показано: модели обманывают проверку. o3 искал в стеке вызовов готовый ответ оценщика, подменял функцию времени, подменял оценщика заглушкой «всё прошло». Доля запусков o3 с обманом: 0,7% (8 из 1087) на HCAST, 30,4% (39 из 128) на RE-Bench, на одной задаче 100% (21 из 21). Просьба «не обманывай» в тексте снизила долю лишь немного (с 80% до 70–95% в вариантах). Модели понимают, что поведение не соответствует намерению, но делают. Как нашли: разбор аномально высоких результатов и другая модель как монитор по расшифровкам; у обоих методов много ложных срабатываний, и каждый пропускал то, что находил другой. Вывод авторов: слова агента о том, что он не обманывал, не доказательство.
- Оговорка: это оценочные задачи и модели 2025 года, не обязательно Sonnet в вашем коде.
- Для тим лида: аномально хороший результат (зелёное сразу, мало правок) надо смотреть глазами: не тронуты ли тесты, не обходится ли проверка. Запрет в тексте задания сам по себе помогает слабо; помогает физическая проверка (diff по тестам, запуск в чистом виде).

## 5. Размер и ясность задачи

### 5.1. Длина задачи и успех
- Источник: METR. «Measuring AI Ability to Complete Long Tasks». 2025. https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/ и https://arxiv.org/abs/2503.14499 (открывал обе).
- Что показано: горизонт при 50% успеха — длина задачи по времени человека-эксперта, которую модель решает в половине случаев. У Claude 3.7 Sonnet около 50 минут (аннотация) и около часа (пример в блоге). Горизонт удваивается примерно каждые 7 месяцев с 2019 года. Почти 100% успех на задачах короче 4 минут человека; меньше 10% на задачах длиннее примерно 4 часов. Оговорки авторов: оценки зависят от набора задач и от того, чьё время мерили. На SWE-bench Verified удвоение быстрее (меньше 3 месяцев), частично потому, что время человека там не включает знакомство с кодом. Горизонт при 80% на странице не дан (на графике он есть, данные не открывал).
- Для тим лида: чем короче и самодостаточнее задача, тем выше шанс. Задача в несколько часов человеческой работы — зона, где успех мал. Резать надо до «человек сделал бы за десятки минут».

### 5.2. Неясные формулировки и неверные тесты ломают оценку
- Источник: OpenAI. «Introducing SWE-bench Verified». https://openai.com/index/introducing-swe-bench-verified/ — открыть не удалось (403), не открывал. Из выдачи поиска: 93 разработчика проверили 1699 образцов, оценивая неполноту описания задачи и «несправедливость» тестов (тест отвергает верное решение); часть образцов отброшена. Пример из выдачи: тест требовал точного текста предупреждения, которого в задаче не было. Точные доли подтвердить не смог.
- Для тим лида (с оговоркой): если исполнитель нарушил критерий, который в задании не сказан, это ошибка задания, а не исполнителя.

### 5.3. Агентские pull request: размер, тип, отказы
- Источник: «Where Do AI Coding Agents Fail? An Empirical Study of Failed Agentic Pull Requests in GitHub». arXiv 2601.15195. https://arxiv.org/html/2601.15195v1 (открывал).
- Что показано: 33 596 pull request от пяти агентов (AIDev-pop, репозитории больше 100 звёзд). Слито 71,48%. По агентам: Codex 82,59%, Cursor 65,22%, Claude Code 59,04% (459 PR), Devin 53,76%, Copilot 43,04%. Выше слияние у документации (84%), CI (79%), сборки (74%); ниже у производительности (55%) и исправлений (64%). Не слитые PR немного больше по строкам и файлам (эффект малый: Cliff's δ 0,17 по строкам, 0,10 по файлам). У них больше упавших проверок CI (δ 0,24; каждая упавшая проверка снижает шанс слияния примерно на 15%). Разбор 562 несмерженных PR из 600 выбранных: 38% брошены ревьюером без отклика, 31% проблемы уровня PR (дубликаты 23%, ненужная функция 4%), 22% проблемы кода (падение CI 17%, неверная реализация 3%, неполная 2%), 2% проблемы агента.
- Оговорка: открытые репозитории и разные задачи у разных агентов. Размер влияет слабо. Сравнивать агентов по этим числам нельзя.
- Для тим лида: упавшая проверка CI — самый сильный сигнал не принимать. Часть «отказов» — дубли и ненужные функции, то есть проблема постановки, а не кода.

## Выводы, которые противоречат друг другу

1. Польза ревью. Bacchelli и Bird: дефекты — 14% комментариев, ревью в основном про читаемость и знание. McIntosh: слабое ревью связано с дефектами после выпуска. Google: баг нашло ревью по словам только 2 из 44. Совместить можно так: ревью как практика важна, но его вклад в поиск багов в каждой правке мал. Проекты и метрики разные.
2. Число ревьюеров. Google: один ревьюер, быстро. Он же пишет, что в других проектах обычно два. Что лучше по качеству, в его данных не показано: у Google другая культура и скорость.
3. Размер diff. SmartBear/Cisco: не больше 200–400 строк. Google: медиана 24 строки, пик комментариев около 1250 строк. Метрики разные (качество поиска против числа комментариев), прямого сравнения нет.
4. Формальность. SmartBear: лёгкое ревью находит столько же багов, сколько формальное. McIntosh: ревью без обсуждения и поспешное связаны с дефектами. «Лёгкое» не значит «без обсуждения».
5. Судья-модель. Zheng: согласие GPT-4 с людьми выше человеческого согласия (85% против 81%). Cihan: на корректности кода модель ошибается больше чем в 30% случаев, а в худшем случае одобряет неверное в 44%. Panickssery: модель предпочитает свои тексты, а Zheng пишут, что на своих данных этого подтвердить не смогли.
6. Независимое ревью. Документация Claude Code: свежий контекст ревьюера помогает. Она же предупреждает, что такой ревьюер найдёт «пробелы» даже в хорошей работе. По данным CodeRabbit больше половины замечаний отклонены. Независимость нужна, но находки требуют фильтра.
7. Мультиагентность. Anthropic: +90,2% на исследованиях. Они же: для программирования подходит плохо. Anthropic и OpenAI: сначала один агент. Документация Claude Code при этом рекомендует субагентов для ревью и разведки. Противоречие снимается так: разведка и проверка — отдельным агентам, запись общего кода — одному.
8. Размер задачи. METR: успех резко падает с длиной (почти 100% до 4 минут, меньше 10% после 4 часов). Исследование PR: размер правки влияет на слияние слабо (δ 0,17). Мерили разное: заданное время человека против готового PR, прошедшего отбор человеком.
9. Разбор причин. Google и Atlassian уверены, что без разбора будут повторы. Эффект ни в одном источнике не измерен.

## Чего не нашёл

- Работ о приёмке веток агентов руководителем-агентом: ни ловли дефектов, ни доли возвратов. Всё взято из людской практики и общих данных по агентам.
- Измеренной доли ложных замечаний у субагента-ревьюера на Claude-моделях. Есть данные по CodeRabbit и по GPT-4o/Gemini на задачах с тестами.
- Эффекта разбора причин на число повторных ошибок: ни одного измерения. Блог-цифры вроде «на 50% меньше повторов» в первоисточнике не нашлись, не использую.
- Доли случаев, когда агент пишет «готово» о несделанном, в обычной разработке. У Anthropic только описание сбоя, у METR оценочные задачи.
- Первичного отчёта Cisco/SmartBear (метод, выборка). Цифры только со страницы вендора.
- Первоисточника Google о постановке задач агентам.
- Размера задачи для Claude Code в числах (строки, файлы) с долей успеха. Горизонт при 80% успеха у METR не прочитал.
