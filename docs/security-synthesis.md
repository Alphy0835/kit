## Что из этого следует для скила

Метка в скобках — откуда.

1. **Безопасника зовут по поводу из правки, а не по памяти тим лида.** Скрипт смотрит дифф и называет поводы: новый
   вход снаружи (маршрут, вебхук, форма), права и роли, секреты и журнал, вызов ИИ и база знаний, зависимости,
   Docker и выкладка, исправление прошлой находки. Есть повод — тим лид зовёт безопасника, и это видно в выводе
   приёмки. (И-1, И-3; С: «выбирает, какие запустить».)
2. **Два шага, два агента.** Первый ищет на полноту и не отсеивает сам. Второй в чистом контексте получает
   находку и код и пытается её опровергнуть; снять находку может только с цитатой защиты из кода. Порог
   уверенности — только на втором шаге. (П: Anthropic 2026, плагин `security-guidance`, Cloudflare, GitHub.)
3. **Модель угроз — файл в репозитории продукта.** Входы снаружи, кто чему доверяет, где деньги (вызовы ИИ),
   где чужие данные. Без неё у одной команды Anthropic 40 % находок были ложными. Шаблон — в `assets/`. (П.)
4. **Доказательство — прогон на локальном стенде или тест, который падает.** Неподтверждённое не выбрасывается,
   а помечается «не подтверждено» с причиной. Рабочий пример атаки почти снимает ложные находки. (П; И-7.)
5. **Узкая задача.** Одна граница доверия или один класс за проход; «есть ли баг» и «достижим ли он снаружи» —
   разные вопросы. Длинный список категорий в промпте снижает число находок. (П.)
6. **Свой список исключений.** Берём фильтр шума Anthropic, но не берём три пункта: «текст пользователя в промпте
   ИИ — не уязвимость», «устаревшие библиотеки не смотрим», «лимиты частоты не нужны». У нас платные токены,
   база знаний и боты в интернете; отказ в обслуживании у нас уже был от собственного исправления. (П; И-3.)
7. **Исправление находки перепроверяет безопасник:** и находку, и то, не сломал ли лимит или проверка доступ
   своим. (И-3.)
8. **Найденный класс — сразу поиск того же в соседних подпроектах.** Защита в одном месте — вопрос «где ещё тот же
   вызов». (И-4; П: «защиту добавили в одну ветку, соседние без неё».)
9. **Обязательное — проверкой, а не строкой правила.** Тест-перепись маршрутов, которая смотрит и право, и то, что
   маршрут отдаёт; сканер секретов по диапазону коммитов; проверка зависимостей при смене lock-файла. Правило в
   тексте — пожелание. (П: OpenSSF, Anthropic SDLC; И-5, И-6.)
10. **Агент-безопасник сам уязвим к инъекции.** Без секретов, с минимумом инструментов, его вывод — данные;
    решение по находке — у тим лида, по выкладке — у владельца. (П: README действия Anthropic.)
11. **Только локальный стенд.** Боевой сервер не трогаем; что можно проверить только на сервере — рунбук
    человеку. (С; И-8.)

## Правила безопасного кода для исполнителя

Отбор: правило есть в двух и более нормативах (У, П) и бьёт в наш класс из истории. Пойдут коротко в
`references/code/security.md`, по одной фразе и случаю; то, что можно, — в проверку.

1. Право проверяет сервер в каждом обработчике, по умолчанию отказ; новый маршрут без права роняет тест-перепись.
   (У ASVS V8, Authorization CS; П; И-2, И-5.)
2. Объект по идентификатору из запроса — сверка владельца; проверить чужим идентификатором. Случайный id — не
   защита. (У API1, ASVS 8.2.2; П; И-2.)
3. Секреты и ПДн не попадают в журнал, текст ошибки, адрес запроса и вывод команды; журнал библиотеки HTTP на
   уровне INFO пишет адрес. (У Logging CS, Secrets CS; П; И-2, И-4.)
4. Запросы к базе только с параметрами; имена колонок и сортировка — из белого списка. (У; П.)
5. В страницу — `textContent`, не `innerHTML`; экранирование под место вставки, кавычки тоже. (У; П; находка
   CB_TASK_076.)
6. Текст из чата, базы знаний и ответа ИИ — данные, не команды; права на базу знаний проверяются до того, как
   текст ушёл в модель. (У LLM01, RAG CS; П; И-2 CB_TASK_306.)
7. Вебхук: подлинность по секрету или подписи по сырому телу, сравнение за постоянное время, окно по времени,
   повтор события не повторяет действие. (У Webhook CS; П; И-2 CB_TASK_142.)
8. Лимит на дорогое — вход, вызов ИИ, рассылку — и лимит не запирает своих. (У ASVS 2.4.1, API4, LLM10; И-3.)
9. Зависимость: проверить, что пакет есть в реестре и это он; закрепить версию; не брать предложенное ИИ вслепую.
   (У A03; П: выдуманных имён 5–22 %.)
10. Не отключать проверку, чтобы заработало; `eval`, `pickle`, `shell=True` на чужих данных — нет. (У; П.)

## Чужое решение, шаблон, пакет

Короткий список вопросов до того, как взять (П, раздел 5; У, раздел 4), и скрипт на бесплатных открытых данных:
- есть ли пакет в PyPI или npm, совпадает ли имя, когда первый релиз и сколько их (deps.dev);
- оценка OpenSSF Scorecard репозитория — подсказка, не приговор;
- известные уязвимости версии (OSV);
- лицензия;
- скрипты установки и сетевые вызовы в коде;
- для скила, правил агента, сервера MCP — прочитать целиком на скрытые команды и сетевые вызовы: это
  исполняемые инструкции.

## Инструменты: что, когда

Всё бесплатное, запуск на машине или локальном стенде, минуты GitHub не тратим. Ставить — только по слову владельца.
- На каждой сдаче, по правке: Ruff `S` или Bandit по изменённым `.py`; Betterleaks по коммитам ветки; OSV-Scanner,
  если менялся lock-файл; Hadolint, если менялся Dockerfile.
- Перед выкладкой, на стенде: OWASP ZAP baseline; `trivy image` (версия закреплена по хэшу, не в Actions);
  полный прогон сканеров кода.
- По поводу: проверка ИИ-бота на инъекции (promptfoo или garak), проверка чужого пакета (выше).
- Не берём: CodeQL (частный код — платно), llm-guard (архив), detect-secrets (не живой), Gitleaks (завершён).
  Правила Semgrep можно гонять у себя, класть в набор нельзя; свои правила — можно.

## Где источники расходятся

- Порог уверенности в один проход (старый промпт Anthropic) против «сначала полнота, потом опровержение» (их же
  статья 2026). Берём второе.
- Роль «ты старший инженер по безопасности»: у Anthropic есть, OpenSSF не советует. Решит проба.
- Самопроверка автором (OpenSSF) против проверки другим агентом (Anthropic, Cloudflare). Обязательная — другим.
- «Закреплять версии» против «не держать компоненты с истёкшим сроком исправления»: закреплять и обновлять по
  сроку риска.

## Что не проверено

- Ни один инструмент и ни один промпт не запускались на нашем коде: ни скорость, ни ложные находки не известны.
- Есть ли у наших сервисов схема OpenAPI (от неё зависит часть проверок стенда).
- Подлинность вебхуков Telegram, MAX и Bitrix24 и отравление базы знаний — в прочитанном нет первоисточников.
- OpenAI (Aardvark, Codex Security) — только пересказы, страницы отдают 403.

## Как проверим скил

Проба на копии «Рабочей»: взять коммиты до исправления настоящих дефектов из И-2 и И-3 (чужой идентификатор,
право маршрута, токен в журнале, подлинность вебхука, лимит, запирающий владельца) и дать безопаснику правку,
которая их внесла. Мера — сколько нашёл, сколько ложных, сколько стоило. Сравнить с официальным плагином
Anthropic `security-guidance` на тех же правках.
