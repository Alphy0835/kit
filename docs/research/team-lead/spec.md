# Источники о технической спецификации, собрано 16.10.2026

Только чтение через веб. Что не открылось или прочитано частично — в конце.

## 1. GitHub Spec Kit (github/spec-kit) — первоисточник

Четыре документа, каждый на своём месте. Адреса: github.com/github/spec-kit, raw `templates/*.md`, `spec-driven.md`.

- **Конституция** (`constitution.md`, один раз на проект): принципы (шаблон — пять слотов), ограничения (стек, безопасность, производительность), порядок работы (ревью, тесты), правила изменения, версия. Пример статей: библиотека-сначала, тесты-сначала, простота («максимум 3 проекта»), «используй возможности фреймворка напрямую, не оборачивай».
- **spec.md** — что и зачем: истории пользователя с приоритетами P1-P3 и проверкой «сам по себе», требования FR-001 (формулировка «MUST»), ключевые сущности, критерии успеха SC-001, допущения. Правило: без решений «как»; неясное помечать `[NEEDS CLARIFICATION: …]`, а не угадывать.
- **plan.md** — как. Разделы: краткое резюме; Technical Context (язык, зависимости, хранилище, тесты, платформа, тип проекта, цели по скорости, ограничения, масштаб); Constitution Check (ворота, проходят до исследования и повторно после проектирования); дерево документов; **дерево исходников с реальными путями** («reference the real directories»); Structure Decision; таблица Complexity Tracking (нарушение, зачем нужно, почему проще нельзя). Рядом: `research.md` (каждое решение с причиной и отвергнутыми вариантами), `data-model.md`, `contracts/` (интерфейсы), `quickstart.md` (как проверить).
- **tasks.md** — формат `- [ ] T012 [P] [US1] Создать модель в src/models/entity.py`: обязательный путь к файлу, метка параллельности, ссылка на историю. Пути берутся из plan, сущности из data-model, эндпоинты из contracts. Фазы: Setup, Foundational (блокирует всё), истории по приоритету, Polish.

Отличие от ТЗ: spec и есть ТЗ («что и зачем»). Plan и tasks — следующие слои. Пишет человек с ИИ в диалоге; меняют, когда сдвигаются требования, затронутые plan помечают или перегенерируют. Поправки конституции требуют обоснования, ревью и оценки совместимости.

**Механические проверки:**
- `analyze` (только чтение, уровни CRITICAL/HIGH/MEDIUM/LOW). Шесть проходов: дубли требований; расплывчатость («быстро», «безопасно» без меры) и остатки TODO/???; недоописанность (задача ссылается на несуществующий компонент); конфликт с конституцией (всегда CRITICAL); пробелы покрытия (требование без задачи, задача без требования); рассинхрон (термины, сущности только в одном документе, противоречие стека).
- `checklist` — «юнит-тесты для требований»: полно, ясно, согласовано, измеримо, покрыты ли сбои. Проверяет качество текста, не код.
- Ворота в plan: нарушение без обоснования или неснятый `NEEDS CLARIFICATION` — «ERROR».

## 2. AWS Kiro specs — первоисточник

Адреса: kiro.dev/docs/specs/, …/feature-specs/, …/best-practices/, kiro.dev/docs/steering/.

- `requirements.md`: истории с критериями в формате EARS: «WHEN [условие] THE SYSTEM SHALL [поведение]». Заявленная цель — ясность, проверяемость, прослеживаемость.
- `design.md`: архитектура и компоненты, диаграммы взаимодействия, модели данных и интерфейсы, выбор технологий, подход к ошибкам, стратегия тестов.
- `tasks.md`: отдельные отслеживаемые задачи с описанием, ожидаемым результатом и зависимостями.
- Steering (`.kiro/steering/`, подключается в каждый запрос): `product.md` (зачем), `tech.md` (стек и ограничения), `structure.md` (организация файлов, имена, шаблоны импорта).
- Один spec на фичу, лежит в репозитории рядом с кодом. Порядок правки: изменить requirements, попросить обновить design, «Sync Files» для tasks. Есть вариант «сначала дизайн», когда архитектура или нефункциональные требования заданы заранее.
- Проверка: «Analyze Requirements» ищет противоречия, неясности, конфликт ограничений, пробелы.

## 3. Anthropic — первоисточник

- «Effective harnesses for long-running agents» (anthropic.com/engineering/effective-harnesses-for-long-running-agents). Агент-инициализатор один раз создаёт `init.sh`, `claude-progress.txt`, первый коммит и **список фич в JSON** (в примере больше 200, все «не проходят»). Исполнитель может менять только поле `passes`; удалять и править тесты — «unacceptable». JSON выбран, потому что модель реже портит его, чем Markdown. Одна фича за сессию; начало сессии: логи git, файл хода, список фич. Это спецификация-контракт для долгой работы, но без архитектуры.
- «Claude Code best practices» (code.claude.com/docs/en/best-practices). Порядок: explore, plan, implement, commit. Планировать, когда меняется несколько файлов или код незнаком; если дифф описывается одним предложением — не надо. Для крупных фич: Claude интервьюирует человека и пишет SPEC.md, исполнение в новой сессии. Прямо: лучшие спецификации самодостаточны, «name the files and interfaces involved», указывают, что вне объёма, и заканчиваются сквозной проверкой. Указывать на существующие образцы в коде. В CLAUDE.md класть «архитектурные решения проекта» и не класть «описание каждого файла». Проверка плана: подагент сверяет дифф с PLAN.md («every requirement is implemented… nothing outside scope changed»).
- «Building effective agents» (anthropic.com/engineering/building-effective-agents). О спецификации почти ничего. Есть: «simplest solution possible», показывать шаги планирования, интерфейсам инструментов уделять столько же внимания, сколько промптам.

## 4. Microsoft и AWS: ADR

- Microsoft Well-Architected (learn.microsoft.com/…/architect-role/architecture-decision-record): запись о решении — постановка с контекстом, рассмотренные варианты, решение с компромиссами и уровнем уверенности, статус (Proposed/Accepted/Superseded). Только решения о структуре, ключевых качествах или трудно обратимые. Журнал «append-only»: принятые не правят, новая запись заменяет старую со ссылкой. Хранить рядом с документацией как «single source of truth».
- AWS Prescriptive Guidance (docs.aws.amazon.com/prescriptive-guidance/…/adr-process.html): ADR на структуру, нефункциональные требования, зависимости, **интерфейсы**, технику построения. Минимум: контекст, решение, последствия. Принятый — неизменяем. Ревью кода сверяется с ADR; нарушившему отдают ссылку. Смысл: ADR объясняет причину и не даёт новым людям переиграть решение.

## 5. Google

- Официального публичного источника о design docs найти не удалось. Единственное — **неофициальная** статья бывшего сотрудника (industrialempathy.com/posts/design-docs-at-google/): контекст и объём; цели и не-цели; сам дизайн (схема контекста, наброски API и хранилища, компромиссы); рассмотренные альтернативы; сквозные темы (безопасность, приватность, наблюдаемость). Писать, когда верное решение неочевидно; 10-20 страниц, мини-док 1-3. Пишет автор системы; правят, пока не выпущено, потом — отдельные дополнения со ссылкой.
- SRE book, гл. 32 (sre.google/sre-book/evolving-sre-engagement-model/) и чеклист запуска (…/launch-checklist/): проверка готовности смотрит на архитектуру и зависимости, метрики и мониторинг, аварийные действия, ёмкость, управление изменениями, производительность. Чеклист запуска: схема архитектуры, ёмкость, «что будет, если» упал узел, мониторинг, обзор безопасности, внешние зависимости и плавная деградация, порядок выкладки. Чеклист «зависит от сервиса», а не жёсткая форма. Это проверка до запуска, а не до кода.

## 6. Не бигтех (по желанию)

- **Superpowers writing-plans** (github.com/obra/superpowers): план для инженера, не видевшего код; карта файлов с одной ответственностью на файл до задач; шапка «Global Constraints» (требования spec копируются дословно); у задачи блок Interfaces (что берёт и отдаёт, точные сигнатуры), перекрёстные ссылки идут на него, а не повторяют код; «Review Focus»; самопроверка (покрытие spec, согласованность имён и типов между задачами, поиск «TBD»).
- **arc42**: 12 разделов — цели, ограничения, контекст, стратегия решения, блоки (структура), время выполнения, развёртывание, сквозные концепции, решения, качество, риски, словарь.
- **C4** (Simon Brown): уровни контекст, контейнеры, компоненты, код. Только способ рисовать.

## Сводка

**Повторяется у 3+ источников:**
1. Цель/контекст и что вне объёма (Spec Kit, Kiro, Google, arc42, Anthropic).
2. Стек и технические ограничения (Spec Kit plan, Kiro tech.md, arc42, Superpowers).
3. Компоненты и границы, структура файлов с реальными путями (Spec Kit, Kiro design и structure.md, arc42, Superpowers, Anthropic «name the files»).
4. Интерфейсы и данные: контракты, модели данных, сигнатуры (Spec Kit, Kiro, Superpowers, AWS ADR, Google, Anthropic).
5. Нефункциональные требования и сквозные темы: безопасность, наблюдаемость, ёмкость (Spec Kit, Kiro, Google, SRE, arc42, AWS ADR).
6. Решения с причинами и отвергнутыми вариантами (Spec Kit research.md, Microsoft и AWS ADR, Google, arc42).
7. Проверка и стратегия тестов (Spec Kit quickstart, Kiro, Anthropic).

**У одного-двух, но полезны агентам:**
- Ворота «конституция»: нарушение допускается только с записью «почему нужно и почему проще нельзя» (Spec Kit).
- Принятые решения не правят, а заменяют новой записью со статусом (Microsoft, AWS).
- Метка «неясно» вместо догадки; блокирует план (Spec Kit).
- Список фич в JSON, агент меняет только `passes` (Anthropic).
- «Global Constraints» дословно и блок «Interfaces» у каждой задачи (Superpowers).
- Одна ответственность на файл, карта файлов до задач (Superpowers).
- Указание на образец в коде, который повторить (Anthropic).
- Уровень уверенности решения (Microsoft).

**Для агентов особенно важно:**
- *Одно место для каждой вещи*: карта «модуль, файл, единственная ответственность» и пути в каждой задаче, взятые из плана. Ближайшее к вашей проблеме с кэшем в двух файлах: Spec Kit (пути в задаче из plan, `analyze` ловит «сущность только в одном документе»), Superpowers (одна ответственность на файл, сверка имён между задачами).
- *Интерфейсы*: сигнатуры и контракты записаны заранее, а задачи ссылаются на них.
- *Запреты*: «вне объёма», «не оборачивать фреймворк», нарушение только с записью причины.
- *Проверяемость*: у требования мера, у спецификации сквозная проверка.

**Что проверяется механически:** `analyze` Spec Kit (покрытие требование-задача, дубли, термины, остатки TODO, конфликт с принципами); ворота plan на `NEEDS CLARIFICATION`; checklist (вопросы да/нет к тексту); «Analyze Requirements» Kiro; самопроверка Superpowers; подагент-ревьюер Anthropic, сверяющий дифф с планом. Скрипта «код соответствует спецификации» в источниках нет, это ревью или тест.

## Что не открылось или неполно

- Kiro: страница concepts дала 404, подробное содержимое `design.md` (разделы) и формат `tasks.md` в официальных страницах описаны кратко; список разделов (архитектура, компоненты и интерфейсы, модели данных, ошибки, тесты) подтверждён страницей requirements-first и сторонними пересказами. Слово EARS в списке документации подтверждено, но полного описания шаблонов нет.
- Spec Kit: `reference/agentic-sdd.html` не открывал, команды `analyze` и `checklist` прочитаны по шаблонам в репозитории; названия команд в README (`/speckit-*`) и в документе `spec-driven.md` (`/speckit.*`) различаются.
- Google: официального источника по design docs не найдено; PRR прочитан по главе 32 (список из шести аспектов), отдельного пошагового PRR-чеклиста не нашёл. Чеклист запуска датирован в самой книге около 2005 г.
- Anthropic «Building effective agents» о спецификации почти ничего не говорит.
- Страницы читались через пересказ малой модели (WebFetch), цитаты выше короткие и из этих пересказов, дословность не гарантирую; чтение документа целиком — только для best-practices Anthropic.
- Microsoft: нашёл ADR в Well-Architected, отдельной страницы Azure Architecture Center по ADR не открывал.
