# Замер возвратов в «Рабочей»: причины и что из них ловит скрипт

Записано 14.10.2026 тим лидом по слову владельца. Замер сделан на репозитории «Рабочая», по текстам замечаний
тим лида, а не по заголовкам коммитов. Он заменяет прикидку из `skill-design.md`, раздел 10: та считалась
по меткам в заголовках на репозитории «Бизнес».

## Коротко

1. **Возвратов 103 на 99 задач, замечаний в них 592.** Период — с 14.08 по 13.10.2026. Принято за это время
   274 задачи. В типичном возврате четыре замечания, три из них — причина возврата.
2. **Скрипт без нейросети ловит 24 % замечаний, ещё 20 % — наполовину, 56 % не ловит.** «Наполовину» значит:
   скрипт показывает подозрительное место, а вывод делает модель.
3. **Скрипт убрал бы целиком только 8 возвратов из 101.** Ещё в 53 он снял бы часть причин. В 40 возвратах
   нет ни одной причины, которую ловит скрипт.
4. **Главная причина возвратов — ошибки логики.** Логика, гонки, плохой ввод и безопасность дают 203 замечания
   из 592. Скрипт ловит из них 4. Тим лид нашёл их чтением кода (151) и живым запросом (30).
5. **Самая частая механическая причина — ветка отстала от `master`.** 47 замечаний в 46 возвратах из 101.
6. **«Нейрослоп» по шаблону почти не встречается.** Зашитые значения — 4 замечания из 592, дубли кода — 4.
   Все нарушения записанных решений об устройстве кода — 24 замечания, скрипт ловит 6.

## Как считал

- **Что такое возврат.** Коммит в `master`, который ставит файлу задачи статус `REWORK`. Текст замечаний —
  строки, которые этот коммит добавил в файл задачи. По заголовкам коммитов находится только 65 возвратов:
  в августе и начале сентября заголовки были другого вида.
- **Сколько.** Найдено 107 событий. Шесть — повторная запись того же текста, они убраны. В двух событиях
  записано по два возврата. Итог: 101 событие, 103 возврата, 99 задач. Объём текста — 417 тыс. знаков.
- **Единица.** Одно замечание: нумерованный пункт или отдельный дефект. Замечания «заодно, в той же ветке»
  учтены отдельно: 211 из 592. Причин возврата — 381.
- **Кто размечал.** Пять субагентов на Sonnet по одной таблице кодов. Тим лид проверил сам все 141 замечание
  с пометкой «ловит», все 118 «наполовину» и 45 случайных «не ловит». В выборке «не ловит» ошибок нет.
  У 31 замечания поправлен код механизма.
- **Что значит «ловит скрипт».** Исполнитель до сдачи запускает скрипт без нейросети, и тот показывает на это
  место. Правило скрипта формулируется без понимания смысла задачи. «Можно написать тест на этот случай» —
  не скрипт, а сама работа; такое записано как «не ловит».
- **Точность.** Разметка — суждение. Доли верны с точностью до нескольких пунктов, порядок причин надёжен.

## Что скрипт не ловит

333 замечания из 592. Почти все — про смысл:

- **Сценарий, который надо придумать.** «Запрос с одним негодным полем успел записать остальные». «Пользователь
  Б оценивает реплику сессии А». «После простоя процесса все накопившиеся лиды получат ответственных разом».
- **Сверка поведения с обещанным.** Документ говорит одно, код делает другое, и оба текста на месте.
- **Пропущенный пункт задания.** Скрипт не знает, что было обещано.
- **Гонки.** 21 замечание, скрипт не ловит ни одного.

Как тим лид находил дефекты кода (логика, ввод, гонки, безопасность — 203 замечания): чтением кода — 151,
живым запросом к запущенному приложению — 30, остальное — сверкой документов и отчётами ревьюера.

В среднем по возврату скрипт снимает четверть причин.

## Оговорки

- **Ветка.** Ни один возврат не вызван только отставшей веткой: это всегда попутная причина. Часто `master`
  уходил вперёд, пока задача ждала приёмки. Проверка у исполнителя перед сдачей этого не увидит — её надо
  повторять в начале приёмки.
- **Паспорта документов.** Проверка «код изменён — документ не тронут» работает, потому что в «Рабочей»
  у документов есть паспорт со списком связанных файлов. Без паспортов проверять нечего.
- **Время.** Возвраты по месяцам: август — 26, сентябрь — 70, октябрь — 5. С 21.09 в возврат идёт только то,
  что блокирует приёмку (решение D-091 «Рабочей»), поэтому в октябре их мало.
- **Мутации.** Проверка дорогая: на каждую мутацию нужен прогон тестов. Половина её находок требует придумать
  нужную мутацию.

## Что из этого следует

Толкование тим лида. Порядок работ решает владелец.

1. **Скрипты не заменят чтение кода при приёмке.** Больше половины причин — смысловые. Скрипт снимает
   с тим лида механику и оставляет время на сценарии.
2. **Порядок скриптов по отдаче:** свежесть ветки, сверка списков, паспорта документов, отчёт и регламент,
   ссылки в документах. Эти пять дают 98 замечаний «ловит» из 141.
3. **Скринер «по шаблону» — самый шумный.** У него 16 точных находок на 36 «наполовину». Каждое правило такого
   скринера надо проверять на ложные срабатывания до включения.
4. **Качество тестов — отдельная тема.** «Тест ничего не сторожит» и «теста нет» — 74 замечания. Механический
   рычаг здесь один: мутации и покрытие изменённых строк. Замер самих прогонов — в `measure-tests.md`.
5. **Для дефектов логики нужен не скрипт, а живой прогон.** 30 дефектов найдены запросом к запущенному
   приложению. Это тип скила «проверка продукта» из `skill-design.md`, раздел 3.

## Где лежат данные

Сырые данные замера в git не кладутся: это рабочие файлы тим лида вне репозитория. Способ повторить: скрипт
берёт коммиты `master`, которые ставят статус `REWORK` в `team/tasks/`, и выписывает добавленные строки.
