# Источники: нормативы и правила написания кода

Собрано 13.10.2026 по слову владельца. Вторая подборка, список открыт. Первая — `ai-code-mistakes.md`.

## Короткий ответ

Правила есть, и их много. Они лежат на четырёх уровнях:

1. **Стандарты качества и безопасности.** Говорят, какие слабые места в коде считаются дефектом. Их пишут
   организации по стандартам: ISO, OWASP, MITRE.
2. **Руководства по стилю.** Говорят, как писать на конкретном языке. Их пишут авторы языка и крупные
   компании: PEP 8 для Python, руководства Google.
3. **Правила ревью и правила о самих проверках.** Говорят, что смотреть в правке и какой должна быть
   автоматическая проверка, чтобы ею пользовались. Google, Meta, NASA.
4. **Готовые наборы правил в инструментах.** Те же правила, уже записанные как проверки. Ruff для Python —
   больше 900 правил. Библиотека детекторов Amazon — 131 детектор для Python.

- Метки проверки те же:
  - **открыт** — страницу открывал сам;

## Стандарты качества и безопасности

**Н-1. ISO/IEC 5055:2021** — открыта страница CISQ, сам стандарт не читал.
<https://www.it-cisq.org/standards/code-quality-standards/>

Международный стандарт, который меряет качество кода по самому коду, без запуска. Его написал консорциум
CISQ, ISO принял без изменений. Измеряет четыре свойства: безопасность, надёжность, производительность,
сопровождаемость. Каждое свойство — это список слабых мест из перечня CWE (Н-2).

Стандарт рассчитан на автоматическую проверку. Это ближайший к нашей идее норматив.

Что страница CISQ относит к каждому свойству:

- **сопровождаемость:** повторяющийся код, высокая цикломатическая сложность, зашитые в код значения
  («hard-coding of literals»), слишком большой компонент, слишком много параметров у метода, повторяющаяся
  бизнес-логика, вызовы в обход слоёв;
- **безопасность:** зашитые учётные данные, непроверенный ввод, SQL-инъекции, отказ от проверенных библиотек;
- **надёжность:** незакрытые ресурсы, обработка ошибок, защита общего состояния в многопоточном коде;
- **производительность:** дорогие вычисления в цикле, соединение без пула.

Точный список слабых мест с номерами лежит в PDF на сайте CISQ. Его не открывал.

**Н-2. CWE Top 25, выпуск 2025** — открыт. Страница обновлена 15.12.2025.
<https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html>

Перечень самых опасных слабых мест в программах. Ведёт MITRE по заказу агентства кибербезопасности США.
Первые десять:

1. CWE-79 — межсайтовый скриптинг.
2. CWE-89 — SQL-инъекция.
3. CWE-352 — подделка межсайтового запроса.
4. CWE-862 — нет проверки прав.
5. CWE-787 — запись за границы памяти.
6. CWE-22 — выход за пределы каталога.
7. CWE-416 — обращение к освобождённой памяти.
8. CWE-125 — чтение за границами памяти.
9. CWE-78 — инъекция команд ОС.
10. CWE-94 — инъекция кода.

Ниже в списке для нас важны: CWE-502 (разбор непроверенных данных), CWE-20 (нет проверки ввода), CWE-863
(неверная проверка прав), CWE-200 (утечка сведений), CWE-306 (нет входа у важной функции).

Номер CWE — общий язык. Им пользуются ISO 5055, OWASP, Ruff, Amazon.

**Н-3. OWASP Top 10:2025** — открыт. Страница даёт только названия.
<https://top10.owasp.org/2025>

Десять главных рисков веб-приложений:

- A01 — нарушение разграничения доступа;
- A02 — ошибки настройки безопасности;
- A03 — сбои в цепочке поставки программ;
- A04 — ошибки шифрования;
- A05 — инъекции;
- A06 — небезопасный замысел;
- A07 — ошибки проверки подлинности;
- A08 — нарушение целостности программ и данных;
- A09 — нет журнала событий безопасности и оповещений;
- A10 — неверная обработка исключительных ситуаций.

Пункт A10 прямо про ошибку 7 из первой подборки: широкий перехват и тихий выход на плохих данных.

**Н-4. OWASP Secure Coding Practices, краткий справочник** — открыт.
<https://owasp.github.io/www-project-secure-coding-practices-quick-reference-guide/stable-en/02-checklist/05-checklist>

Готовый проверочный список: 14 разделов, 218 пунктов. Разделы: проверка ввода, кодирование вывода, вход
и пароли, сеансы, разграничение доступа, шифрование, обработка ошибок и журнал, защита данных, защита
связи, настройка системы, база данных, файлы, память, общие правила.

Примеры пунктов по разделам инструмент назвал сам. Это его пересказ, а не текст справочника. Сверить
с оригиналом.

**Н-5. The Twelve-Factor App, раздел «Config»** — открыт. Автор — Адам Уиггинс, сооснователь Heroku.
<https://12factor.net/config>

Самое точное правило о зашитых значениях.

- Настройка — всё, что меняется между развёртываниями: адреса баз и служб, учётные данные, имя сервера.
- Настройка хранится в переменных окружения, отдельно от кода. Постоянные в коде запрещены.
- Проверка: код можно в любой момент открыть всему миру, и ни один секрет не утечёт.
- Внутреннее устройство приложения, которое не меняется между развёртываниями, остаётся в коде.

Последний пункт отвечает на вопрос, что не считать хардкодом.

## Руководства по стилю

**Ст-1. PEP 8 — Style Guide for Python Code** — открыт. Действующий документ. Авторы: Гвидо ван Россум,
Барри Уорсо, Алисса Коглан.
<https://peps.python.org/pep-0008/>

Правила из раздела «Programming Recommendations», которые проверяются скриптом:

- называть конкретные исключения; голый `except:` — только чтобы записать ошибку в журнал или убрать за
  собой и пробросить её дальше;
- в блоке `try` держать как можно меньше кода;
- `None` сравнивать через `is`, а не через `==`;
- тип проверять через `isinstance`;
- булево значение не сравнивать с `True` через `==`;
- не выходить из блока `finally` через `return`, `break`, `continue`: это глушит ошибку;
- ресурсы открывать через `with`.

Числовые правила: строка до 79 знаков, отступ четыре пробела, имена `l`, `O`, `I` запрещены.

Документ сам называет, когда правило не применять: когда оно ухудшает читаемость и когда соседний код
написан иначе. Порядок важности: единообразие внутри функции и модуля, потом внутри проекта, потом
с руководством.

**Ст-2. Google Python Style Guide** — открыт.
<https://google.github.io/styleguide/pyguide.html>

Строже, чем PEP 8. Правила, которые закрывают ошибки из первой подборки:

- 2.1 — прогонять `pylint`; отключать предупреждение можно только на одной строке и с объяснением;
- 2.4 — не ставить голый `except:` и не ловить `Exception`, если ошибка не пробрасывается дальше;
- 2.4 — не проверять условия через `assert`;
- 2.5 — избегать изменяемого общего состояния;
- 2.12 — не брать изменяемый объект значением по умолчанию;
- 2.21 — типы у открытых функций обязательны;
- 3.12 — `TODO` только со ссылкой на задачу;
- 3.16 — однобуквенные имена запрещены, кроме счётчиков цикла и нескольких названных случаев;
- 3.18 — функцию длиннее примерно 40 строк стоит делить. Это совет, а не предел;
- 3.19.7 — `# type: ignore` только точечно.

**Ст-3. Google TypeScript Style Guide** — открыт.
<https://google.github.io/styleguide/tsguide.html>

- `any` избегать: брать точный тип или `unknown`; отключение проверки — только с объяснением;
- вместо приведения типа через `as` и вместо `!` — проверка при работе; приведение — с комментарием,
  почему оно безопасно;
- `@ts-ignore`, `@ts-expect-error` и `@ts-nocheck` запрещены;
- пустой блок `catch` запрещён; если делать нечего, нужен комментарий с причиной;
- бросать можно только `Error` и его наследников;
- `eval` и `Function(...строка)` запрещены;
- `var` запрещён; сравнение только через `===`;
- `debugger` в рабочем коде запрещён.

## Правила ревью и правила о самих проверках

**П-1. Google Engineering Practices — What to look for in a code review** — открыт.
<https://google.github.io/eng-practices/review/reviewer/looking-for.html>

Открытое руководство Google о том, что проверяющий смотрит в правке. Пункты, которые совпадают с ошибками
ИИ:

- **Сложность.** Отдельно названо «over-engineering»: общность и возможности, которые системе сейчас не
  нужны. Решать надо сегодняшнюю задачу, а не возможную завтрашнюю.
- **Тесты.** Тест должен падать, когда код сломан. Тесты идут в той же правке, что и код.
- **Комментарии.** Комментарий объясняет «зачем», а не «что». Устаревшие `TODO` убирают.
- **Стиль.** Крупное переформатирование не смешивают с правкой по делу.
- **Единообразие.** Где руководство молчит, пишут как в соседнем коде.
- **Работа кода.** Проверяющий сам думает о крайних случаях и гонках. Скриптом это не заменить.
- **Общее правило.** Правку, которая ухудшает состояние кода, не принимают.

**П-2. Software Engineering at Google, глава 20 «Static Analysis»** — открыт.
<https://abseil.io/resources/swe-book/html/ch20.html>

Книга инженеров Google. Глава о том, как устроены автоматические проверки кода в компании. Это готовые
требования к скринерам.

- **Ложная находка — та, после которой человек ничего не сделал.** Верное, но бесполезное предупреждение
  тоже считается ложным.
- **Порог: меньше 10% таких находок у каждой проверки.** По всей системе Google — чуть меньше 5%. Проверки
  с шумом выше порога люди перестают читать.
- **Показывать при ревью.** Это главное место: человек уже правит код, проверяющий может потребовать
  исправить.
- **Только новое.** Проверка смотрит строки, которые тронула правка. Старый работающий код чинить опасно.
- **Находка с готовым исправлением.** Оно же объясняет, что не так. Авторы применяют такие исправления
  около 3000 раз в день.
- **Стиль чинит программа, а не человек.**
- **Проверки пишут сами команды.** В системе больше 100 анализаторов, большинство написали не её авторы.
- **Проверка без единой ложной находки становится ошибкой сборки.** Предупреждения сборки люди не читают.

**П-3. Scaling Static Analyses at Facebook** — открыта страница Meta с аннотацией, статью не читал. Журнал
Communications of the ACM, 29.07.2019. Авторы: Дино Дистефано, Мануэль Фендрих, Франческо Логоццо.
<https://research.facebook.com/publications/scaling-static-analyses-at-facebook/>

Meta о двух своих анализаторах: Infer ищет падения, Zoncolan — дыры в безопасности. Оба работают как
роботы на ревью каждой правки. Infer: больше 100 тысяч находок исправлено до выпуска.

По выдаче, не сверено: когда находки показывали при ревью, исправляли около 70%; когда тот же список
отдавали разработчикам отдельно — почти ничего. Цифру нашёл только в чужой статье, которая ссылается на
Meta.

**П-4. The Power of Ten — Rules for Developing Safety Critical Code** — открыт, прочитан целиком. Автор —
Джерард Хольцман, лаборатория надёжных программ NASA/JPL.
<https://spinroot.com/gerard/pdf/P10.pdf>

Десять правил для кода, от которого зависит жизнь. Написаны для языка C, нам важны не сами правила, а
доводы автора:

- Обычное руководство содержит больше ста правил и почти не влияет на то, как люди пишут код.
- Главный порок руководств: их нельзя проверить программой. Вручную сотни тысяч строк никто не прочтёт.
- Правил должно быть мало, не больше десяти. Каждое — настолько точное, чтобы его проверяла программа.
- К каждому правилу дано обоснование.

Правила, которые переносятся на любой язык:

- 4 — функция помещается на один лист, около 60 строк;
- 5 — проверки условий внутри кода, в среднем не меньше двух на функцию; бессмысленная проверка вроде
  `assert(true)` правило нарушает;
- 6 — данные объявляются в самой узкой области видимости;
- 7 — возвращаемое значение функции проверяется; входные параметры проверяются внутри функции;
- 10 — код собирается без единого предупреждения и каждый день проходит анализатор с нулём находок. Если
  анализатор ошибся, код переписывают так, чтобы он стал понятен анализатору.

Правило 5 спорит с ошибкой 5 из первой подборки («защита от невозможного»). Хольцман требует таких
проверок для кода, от которого зависит жизнь. Anthropic считает их лишними в обычном коде. Противоречия
нет: разный уровень риска.

**П-5. Lessons from Building Static Analysis Tools at Google** — по выдаче. Журнал Communications of the
ACM, 2018.
<https://research.google/pubs/lessons-from-building-static-analysis-tools-at-google/>

Статья тех же авторов, что и глава П-2. Причины, по которым проверки бросают: инструмент не встроен в
работу, долго работает, ему не верят из-за ложных находок. Вывод: мало найти ошибку, надо сразу
предложить исправление.

## Готовые наборы правил

**И-1. Ruff, список правил** — открыт, страница прочитана наполовину.
<https://docs.astral.sh/ruff/rules/>

Линтер для Python с открытым кодом. По странице — больше 900 правил. Правила собраны в семейства, каждое
семейство — перенос известного инструмента.

Семейства по нашим темам:

- `S` — безопасность (правила инструмента Bandit);
- `BLE` — слепой перехват исключений;
- `B` — вероятные ошибки;
- `C90` — сложность функций;
- `ERA` — закомментированный код;
- `T20` — оставленный `print`, `T10` — оставленный отладчик;
- `ARG` — неиспользуемые параметры;
- `FIX` и `TD` — метки `TODO` и `FIXME`;
- `N` — имена, `D` — описания функций, `ANN` — типы;
- `PL` — правила Pylint, `TRY` — оформление обработки ошибок.

Правила, коды которых я видел на странице:

- `BLE001` — пойман `Exception` целиком;
- `S110` — `try … except: pass`; `S112` — `try … except: continue`;
- `S105`, `S106`, `S107` — зашитый пароль;
- `S101` — `assert` в рабочем коде;
- `S102` — `exec`; `S307` — `eval`;
- `B006` — изменяемое значение по умолчанию;
- `ERA001` — закомментированный код;
- `T201` — `print`.

Коды для «магических чисел», неиспользуемых импортов и слишком длинных функций на прочитанной половине
страницы не показаны. Они есть, но номера я не сверял.

**И-2. Библиотека детекторов Amazon Q, Python** — открыт.
<https://docs.aws.amazon.com/codeguru/detector-library/python/>

Открытый перечень проверок, которыми Amazon разбирает код. Для Python — 131 детектор. У каждого своя
страница с описанием и примером. Детекторы по нашим темам:

- зашитые учётные данные; учётные данные открытым текстом; зашитый IP-адрес;
- исключение поймано и проглочено; слишком общий перехват; плохая обработка ошибок;
- изменяемый объект значением по умолчанию;
- незакрытый ресурс;
- сложный код, который трудно сопровождать; опасные глобальные переменные;
- секреты и личные сведения в журнале;
- SQL-инъекция, инъекция команд ОС, выход за пределы каталога, разбор непроверенных данных.

Детектора повторяющегося кода в списке нет.

**Не открывал:** списки правил ESLint и typescript-eslint, Bandit, Semgrep, gitleaks. Это такие же
готовые наборы для JavaScript, безопасности Python и поиска секретов.

## Что из этого видно

Всё ниже — мои выводы, а не слова источников.

1. **Ошибки ИИ — не новые ошибки.** Почти на каждую есть правило, написанное до нейросетей. Широкий
   перехват запрещает PEP 8. Зашитые значения — Twelve-Factor и ISO 5055. «Over-engineering» названо
   в руководстве Google по ревью.
2. **Большую часть ошибок с оценкой «да» уже ловят готовые инструменты с открытым кодом.** Писать их
   заново незачем: достаточно включить нужные правила Ruff и дать тим лиду одну команду. Лицензии я не
   проверял.
3. **Свои скринеры нужны там, где готового нет.** Это огрехи, которые появились вместе с агентами:
   удалённые и пропущенные тесты, выход за рамки задачи, лишние файлы после работы, опасные команды в
   журнале, шаблонный интерфейс, подгонка под тесты.
4. **Правил должно быть мало.** NASA: больше десяти правил люди не держат в голове. Google: проверку
   с шумом выше 10% перестают читать. OpenAI: один большой файл правил не сработал. Три источника из
   разных лет говорят одно.
5. **Требования к скринеру уже сформулированы.** Смотреть только строки правки. Показывать при приёмке.
   Давать находку вместе с исправлением. Считать ложной любую находку, после которой ничего не сделали.
6. **Три ошибки не ловит ни один норматив и ни один скрипт:** пропущенные крайние случаи, неверная логика,
   пропущенная проверка прав. При этом пропущенная проверка прав стоит четвёртой в CWE Top 25 и первой
   в OWASP Top 10.
