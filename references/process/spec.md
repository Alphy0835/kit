# Спецификация

Открывай, когда начинаешь новый проект, подпроект или большую фичу. Большая — та, что задевает больше одного модуля,
вводит новое хранилище, внешнюю систему или новый общий список. Спецификация пишется до того, как ты режешь работу на
задачи.

Статус: черновик от 16.10.2026, не испытан. Шаблоны — `assets/spec-template.md` и `assets/decision-template.md`.
Проверка — `scripts/lead/spec_check.py`, границы в коде — `scripts/lint/boundaries.py`.

Спецификация отвечает на вопрос «как и где». ТЗ продакта отвечает на «что и зачем». Нарезка на задачи идёт после
спецификации и ссылается на неё.

## 1. Сначала спецификация, потом задачи

Сначала тим лид пишет спецификацию. Потом владелец её подтверждает. Только после этого тим лид нарезает задачи.
Первая задача — каркас: папки из карты модулей, пустые модули с файлами входа, раздел `[boundaries]` в
`kit.toml` и команда запуска. Остальные задачи пишут код в готовые места.

Границы проверяются при каждой сдаче, а не один раз. `handoff/check.py` запускает `scripts/lint/boundaries.py` по
карте, нарушение — стоп. В проекте, где нарушения уже есть, они записываются списком: из списка проходит, новое —
стоп, исправленное вычёркивается в той же ветке. Добавить нарушение в список можно только руками, и это видно в
правке.

Почему. Коннектор нарезали на 46 задач, а границы модулей задали через три дня, когда десяток задач уже шёл. К
этому дню 20 из 45 связей между модулями шли во внутренние файлы, а один общий файл запросов обслуживал все
модули. Ушло три задачи-переделки и 77 функций переехали к владельцам. Ещё 32 задания пришлось дополнять.
В ядре карта границ появилась примерно на 172-й задаче, циклы остались до сих пор. Подпроект, где каркас и тест
границ сделали в первой задаче, возвратов по границам не получил.

## 2. У каждой вещи одно место

Над картой — строка «Как делим папки». По умолчанию: сверху `docs/`, `backend/`, `frontend/`, `design/`, внутри —
папка на каждую функцию продукта. Иначе — напиши, как и почему.

Карта модулей — таблица: путь, за что модуль отвечает (одна фраза), вход, кого модуль может вызывать. Вход — один
файл, через который другие модули зовут этот; «весь модуль» — для общего кода без внутренностей. «Может
вызывать» пишется со стороны того, кто зовёт: «A берёт только из B и C». Такое правило проверяет скрипт, а
«кому можно звать меня» — нет. Карта не разрешает круг.

Данные — таблица: сущность, где хранится, какой модуль её меняет. Каждая сущность, кэш и список принадлежат одному
модулю. Другой модуль получает их через этот модуль, а не заводит свою копию.

Почему. Кэш версий жил в двух файлах под разными именами, починили один. Дефект пропустили оба скила на пробе
приёмки. Два вида номера одного чата — ключ коннектора и номер портала — дали четыре возврата: заглушка в тестах
принимала любой номер.

## 3. Словарь — одно имя на одну вещь

Раздел «Словарь»: термин, что он значит, как он называется в коде, на экране и у заказчика. Виды
идентификаторов — отдельной строкой: откуда номер берётся и где его можно подставлять.

Почему. Одно слово у нас и у заказчика означало разное. Подпись на экране расходилась с руководством. В коде
оказалось одно имя вместо другого. Это минимум семь возвратов.

## 4. Общие списки — «что менять, когда добавляешь»

Таблица: «добавляешь настройку, маршрут, миграцию, право, текст» → какие файлы и тесты меняются вместе.

Миграции — набор строк в разделе «Данные»: где лежат, как именуются, файл последней миграции, команда создания.
Каждая новая миграция правит одну строку в файле последней миграции. Две ветки, которые взяли один номер, правят
одну строку — git показывает конфликт, а `handoff/check.py` (раздел `[[migrations]]` в `kit.toml`) — стоп. Задание,
которое создаёт миграцию, называет этот файл; две такие задачи тим лид не пускает как независимые. Выложенную
миграцию не правят. Удаление колонки или таблицы — в два шага, в разных выкладках.

Почему. Шесть событий с забытым списком или переписью, два из них кончились откатом слияния. Номер миграции из
одного общего списка дал 11 столкновений, пять из них за три дня при четырёх параллельных ветках. Это
столкновение заложено в схему, а не в исполнителя.

## 5. Стек — с версиями и запретами

Язык, библиотеки, хранилище, способ запуска и тестов, с версиями, как в рабочей среде. Рядом — «чего не
использовать» и почему. Стек — развилка с рекомендацией для владельца. Ты не выбираешь его молча.

Почему. В регламенте проекта раздел «Стек» остался незаполненным, а стек описан только у двух подпроектов из пяти.
Тест, зелёный на новой версии языка, оказался красным на версии в образе.

## 6. Неясное помечаешь, а не угадываешь

То, что не решено, пишешь в спецификации меткой «не определено: …» и указываешь, кто решает. Часть
спецификации с такой меткой на задачи не режешь.

Почему. В GitHub Spec Kit неснятая метка неясности останавливает план. Догадка в спецификации переходит во
все задачи сразу. Ошибка в подробном описании переходит в код, это пишет и Anthropic.

## 7. Задание ссылается на спецификацию

В задании есть поле «Спецификация»: какой раздел и какие пути из карты модулей задача меняет. Путь вне карты
означает, что сначала правится спецификация.

Почему. В 19 % заданий трёх подпроектов не было ни файла, ни модуля, где делать. Это грубый подсчёт по тексту.
В GitHub Spec Kit каждая задача называет путь из плана.

## 8. Спецификацию меняешь в той же ветке, решение — новой записью

Новое требование, переезд модуля или смена хранилища сначала меняют спецификацию, потом задачи.

Каждое решение — свой файл `decisions/NNNN-название.md` по `assets/decision-template.md`. В спецификации — только
ссылки. Принятую запись не переписываешь: заводишь новую со ссылкой на старую и причиной, у старой меняешь только
статус на «заменено NNNN». Номер не используется повторно. Записываешь решение о структуре, хранилище, внешней
системе и то, что трудно отменить; мелочи — в задании.

Путь, который пробовали и бросили, тоже записывается — в разделе «Что отвергли и что не сработало»: что сделали,
где след (задача, коммит), что вышло и почему бросили. Бросили после того, как на путь ушла задача, — запись
обязательна, даже если решение мелкое. Если от пути отказались после принятия, новая запись заменяет старую.

Почему. Решения о структуре в проекте пересматривались на ходу: прямой канал построен за шесть задач и через
неделю отменён. Настройки переведены на версии за 14 задач. Панель пересобрана дважды за три дня без описи экранов,
и при пересборке пропали 48 настроек. Часть из этого — честно новые требования. Но там, где спецификации не
было, никто не видел, что именно переезжает. Брошенный путь записываем по слову владельца: чтобы не ходить
по кругу и любой видел, что уже пробовали.

## 9. Сценарии, совместимость, риски — коротко, но всегда

- Сквозные сценарии: два-три главных пути через модули, по шагам. Каждый шаг — модуль из карты.
- Совместимость: что уже работает у людей и не должно сломаться — записи в базе, ссылки, внешние клиенты,
  настройки — и чем это проверяем. Проект новый — «нет, проект новый».
- Риски и долг: что может не получиться и что откладываем, с тем, когда вернуться. Нет — «нет».
- В шапке — владелец: кто подтверждает спецификацию и снимает «не определено».

Почему. Сценарий показывает, какие модули задача задевает вместе. Записи, созданные до правки, уже ломали приёмку:
режим по умолчанию не включался у тех, у кого запись стояла со старым значением. Риск, не записанный в начале,
всплывает задачей-переделкой.

## 10. Схема системы — до задач

Раздел «Схема системы» — одна схема Mermaid: части, которые запускаются отдельно (сервис, база, очередь, бот,
панель), внешние системы и люди. Внутренности частей не рисуешь: они в карте модулей. Схема — между частями.

- Каждая стрелка — одно направление и подпись: что передаёт, как (HTTP, событие, файл) и чем вызывающий
  доказывает, кто он (свой секрет, общий секрет, подпись, сессия, ничего).
- Границы доверия — рамки `subgraph`: интернет, наш сервер, чужая система. Стрелка через рамку — вход снаружи,
  у него строка в модели угроз (`references/security/threat-model.md`).
- Над схемой — что на ней и чего нет. Вид схемы — `flowchart LR`. Синтаксис C4 в Mermaid не берёшь: он
  помечен как пробный и не даёт управлять раскладкой.
- Нарисовал — пройди по стрелкам и запиши в «Не определено» то, что не смог подписать.

Схема — текст в файле спецификации. GitHub рисует её сам, правится в той же ветке, что и код (правило 8).
Задача добавляет часть, хранилище, внешнюю систему или стрелку — схема меняется в её ветке.

Почему. У C4 стрелка между частями всегда подписана технологией, у Microsoft модель угроз начинается со схемы
потоков с границами доверия. При разборе такой схемы недостающую часть находят за минуты. Наш замер — в
`docs/probes/team-lead/diagram.md`.

## Когда не применять

Правка, которую можно описать одним предложением, или правка внутри одного модуля без новых данных и списков. Тогда
хватит задания. Так же советует Anthropic: если правку можно описать одной фразой, план не нужен.

## Что из этого проверяет скрипт

`scripts/lead/spec_check.py` — сама спецификация:
- обязательные разделы на месте и не пустые;
- каждый путь и вход из карты есть в репозитории; папка на верхнем уровне корней карты, которой нет в карте, —
  предупреждение;
- есть строка «Как делим папки» и колонки «Вход» и «Может вызывать»; в «Может вызывать» только модули карты;
  карта не разрешает круг;
- «Данные» говорят о миграциях — есть файл последней миграции;
- «Решения» — ссылки на файлы, файлы есть;
- метки «не определено» перечисляются, чтобы ты видел, что ещё нельзя резать;
- в шапке есть «Владелец»; модуль из «Сквозных сценариев» есть в карте;
- «Схема системы» — блок Mermaid `flowchart` без заготовок; стрелка без подписи и схема без рамок —
  предупреждение. Правду подписи скрипт не видит: «общий секрет» на четырёх стрелках замечаешь ты;
- с `--task <номер>`: в задании есть поле «Спецификация», пути из задания лежат внутри карты, задание о миграции
  называет файл последней миграции.

`scripts/lint/boundaries.py` — код против карты, при каждой сдаче через `handoff/check.py`: импорт Python или
относительный импорт JS/TS в модуль не из «Может вызывать», мимо входа, круг между модулями; вложенный модуль
проверяется как отдельный; импорт из модуля в код вне карты — предупреждение. Правила по имени («из фасада бери
только это») и «в таблицу пишет только этот модуль» скрипт не видит — их ты проверяешь при приёмке.
